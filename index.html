Perspective

“Believe those who are seeking the truth, doubt those who find it.” — André Gide

Your testing framework can pass every test at every layer and still produce the wrong number. Someone has to test the tests.

Structure Tests Pass, the Answer Is Still Wrong

Every layer was green. The number was still wrong.

Your pipeline can pass every test at every layer and still put the wrong number on the dashboard. I have watched it happen more than once, and the postmortem always opens with the same awkward silence: every check was green.

We shifted testing left, and we were right to. There are contracts at ingestion now. There are dbt tests on Bronze, validations on Silver. Schema, nulls, uniqueness, freshness, row counts. Every layer reports green. So here is the question nobody enjoys: if every layer passed, why is the number on the dashboard wrong?

Because passing each layer does not compose into a correct output.

Three things I have seen break a clean pipeline:

A join fans out and doubles your revenue. Every row is still valid. Every field is still well-formed. The total is twice what it should be, and not one test fired.

A filter silently drops a segment. Every surviving row passes every check, because the rows that would have failed are simply gone. The data that remains is pristine. It is also incomplete, and nothing on the dashboard says so.

An aggregation rolls up over a null-filled column. The sum is clean. The math is wrong. Null is not zero, and the average you are reporting quietly excludes the rows you most needed to count.

Each of these tests asks the same narrow question: is this field well-formed? None of them asks the only question the business actually cares about: is the answer someone is about to read actually true?

We got very good at testing structure. We barely test meaning. And somewhere along the way we assumed that clean inputs plus green transforms equal correct outputs. That is not a data quality strategy. It is a logic error with a CI badge.

The missing layer is not another null check. It is reconciliation against what the business expects to be true. Does total volume tie back to the system of record? Does this KPI match the number finance closed on last quarter? If I sum the parts, do I get the whole?

In capital markets this is not optional. You tie position totals back to the book of record. You reconcile a P&L figure to what finance signed off on. You replay the legs and check that they sum to the trade. The structural checks tell you the data is shaped correctly. The reconciliation tells you it is right. Those are different claims, and only one of them is what a trader or a CFO is relying on.

Structural correctness is necessary. It was never sufficient.

So when your dashboard is wrong, be honest about which failure it was. Did a test fail, or did every test pass and nobody checked the result?

Who Tests the Tests?

If nothing ever fails, how do you know your checks still work?

A few years ago I inherited a monitoring system with more than 200 data quality rules. The dashboards glowed green. Leadership was confident. The system had been "stable" for years.

I was skeptical. If nothing ever fails, how do we know the rules still work?

So I ran an experiment. I deliberately injected bad data. Nulls in key fields. Duplicates where keys were supposed to be unique. Values well outside any sane range. Broken referential integrity between tables that were supposed to agree.

A large share of the rules never fired. The dashboard stayed green while I was actively corrupting the data underneath it. Those rules had not been protecting anything for a long time. They were decoration with a nice color scheme.

This is the gap almost no one owns. Most organizations have QA validating code paths, Data Quality validating datasets, Observability tracking metrics, and Governance defining policies. Everyone trusts the safety net. No one tests the net itself.

And the failure modes are quiet by design. Test frameworks run clean while skipping the edge cases that matter. Checks stay green while the logic underneath them drifts. "Certified" datasets keep passing long after the assumptions behind the certification changed. The pipeline succeeds. The output is wrong. When your validation layer is not itself tested, you do not have quality. You have false confidence with CI/CD attached.

The fix is to treat validation like production code, because that is what it is.

Meta-QA: test your test framework the way you would test any other system. Prove it fails when it should.

Rule versioning: track when a rule changed and why, so you can see logic drift instead of discovering it at 3 AM.

Mutation testing: borrow the practice directly from software. In code, you deliberately break the logic to confirm the tests catch it. In data, almost nobody does this. So do it. Inject the fault on purpose, and confirm the alarm goes off. A rule that has never caught a failure is a hypothesis, not a control.

Cross-layer validation: align the code, the data, and the business meaning, so a number that is structurally valid still has to be true.

Consumer simulation: replay how the data is actually used, not just how it is stored.

Here is the uncomfortable shift underneath all of this. QA, SDET, and Data Quality are becoming the same discipline. In production, a bad outcome does not care whether it came from a code bug, bad data, or a broken assumption. The impact is identical. Treating them as separate teams with separate dashboards is how the gap stays open.

So if your dashboards have been green for months, one of two things is true. Your system is flawless, or your validation layer is irrelevant. You already know which is more likely.

The real question is about authority, not tooling. When something looks wrong, who gets to say "this is incorrect" and stop the release? Or does everyone wait for production to decide for them?

I Let an LLM Write My Data Quality Rules

It was fast. Most of it was reasonable. That is exactly the problem.

I let an LLM write my data quality rules. Here is what scared me.

It was fast. Genuinely impressive. I described a dataset, and in seconds it produced 40 validation rules. Null checks, range checks, referential integrity, distribution bounds. Most of them were reasonable.

That is the problem. "Reasonable" and "correct" are not the same thing, and an LLM cannot tell you which rules it got wrong. It can only tell you they all look right.

Look at what it gave me.

It flagged a field that should never be negative. Correct in general, except in our data negative values were legitimate reversals. The rule would have fired on perfectly good records.

It set a row-count tolerance. Reasonable, except it had no idea that volume drops on settlement holidays. The rule would have screamed every time the market was closed and stayed silent on the days that actually mattered.

It checked a join key for uniqueness. Right in principle, except it did not know which of two near-identical keys was the real one. It validated the wrong column with great confidence.

None of these are model failures. They are context failures. And context is exactly what the model does not have. It does not know your settlement calendar. It does not know your corporate actions. It does not know the vendor who sends nulls on holidays or the one who recycles identifiers every quarter.

Here is where I landed. An LLM can generate a thousand rules. It cannot tell you which one would have caught last quarter's incident. That is still your job.

So we did not remove the analyst by adding the LLM. We moved the analyst from writing rules to interrogating them. From typing out forty null checks by hand to asking which forty actually protect the number the business depends on. That is a better job. It is not a smaller one.

The danger is not that the model is wrong. The danger is that it is plausible. A rule that looks right and ships without anyone checking it against the real world is worse than no rule at all, because now you have a green check standing guard over an assumption nobody verified.

Use the model to suggest. Keep the authority to decide.

So the question I would put to any data team reaching for this: would you trust an LLM to define "correct" for your most critical dataset? Or only to suggest it?

Automation Killed Accountability

We automated execution and quietly deleted the person whose job was to ask how it breaks.

Shift left. Engineering owns quality. Automate everything.

We have heard these for years, and there is truth in all of them. But here is the uncomfortable part nobody puts on the slide: somewhere in that shift, we stopped having anyone whose job was to think about failure.

The pattern shows up the same way across teams and across industries. We automated execution. We optimized delivery. We bought dashboards. And we quietly removed the role whose entire job was to ask one question: how can this break?

In software, that role used to be the QA Analyst. In data, it was the Data Quality Analyst. Not the person who ran the scripts. The person who sat with the requirements before a line was written and asked what the 15 ways this could go wrong were, where the boundaries lived, and which scenarios never came up in the meeting.

Then we reorganized. We replaced QA Analysts with SDETs. We told developers to own quality. We bought tools, dashboards, and frameworks. All reasonable moves on their own. But look at who designs the test cases now.

Product owners write acceptance criteria, but they are not trained testers. Developers test the paths they built, and they test the happy ones, because they already believe the code works. SDETs automate those criteria into scripts, but automating a test is not the same as challenging whether the test is the right one. So who is left to ask how it breaks?

In a lot of organizations, the honest answer is nobody. The analytical layer got orphaned. Execution has three owners and strategy has none.

The same gap opened in data, just a few years later. Companies invested heavily in pipelines. They hired Data Engineers to build them. They bought observability platforms that surface every metric you could want. But who defines what correct data actually looks like?

Data Engineers move and transform data. That is the job, and it is a hard one. It does not always include stopping to ask whether this field should ever be negative, what happens when a vendor sends nulls on a holiday, or why row counts dropped 40 percent last night. Was that a failure, or was it seasonality? Tools can tell you the number moved. Only a person can tell you whether it was allowed to.

That is the distinction we keep missing. Tools can monitor data. Only people can define correctness.

So when something breaks, teams do not debug the logic anymore. They debug the alerts. They ask which threshold tripped and whether it can be tuned, instead of asking what assumption was wrong. That is not quality engineering. That is alert-driven development, and it only tells you about the failures someone already thought to instrument. The ones nobody anticipated stay invisible, because anticipating them was the job we deleted.

Software QA says we automated the tests. Data Quality says we implemented the checks. Observability says the dashboards are green. So when something goes wrong, everyone points at tooling, and no one points at a decision.

That is the real shape of the problem. Most organizations do not have a quality problem. They have a responsibility problem. The checks exist. The dashboards exist. What is missing is a person with the authority and the mandate to look at a result and say this is wrong, and to stop the release before it ships.

Automation did not eliminate bad quality. It eliminated accountability for it. We spread execution across four roles and left ownership of correctness with none of them.

You can buy every tool on the market and still not answer the only question that matters at 3 AM. If no one has the authority to say this is wrong, then quality does not exist in your organization. You just have not been caught yet.

So ask it plainly about your own team. When the next bad number ships, will someone own the decision that let it through? Or will everyone point at the dashboard that stayed green?
